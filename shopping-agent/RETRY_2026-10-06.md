# Page adapter v0.2 retry — October 6, 2026

> Retrospective correction: these runs verified cart execution under an expanded recommendation/substitution prompt, not full satisfaction of the original shopping request. A beanie, cap or sunglasses does not fulfill the mug need. Token comparisons excluding cached input also require checking initial cache conditions; the Sol pair had unequal initial cache hits. See [the prompt and measurement audit](PROMPT_AND_MEASUREMENT_AUDIT_2026-10-06.md).

A fresh `gpt-6-luna` agent at `xhigh` completed the same PrestaShop task in **215.293 seconds**, using **78,927 tokens excluding cached input** and **15 browser interactions**. It searched, read details, compared images, added three products and verified the basket from the starting page. Its only document navigation was the final native cart handoff.

Compared with the prior adapter run, that is 12.7% less time, 27.1% fewer tokens excluding cached input, and 21.1% fewer browser interactions. It was still 3.235 seconds slower and used 30.6% more uncached tokens than the previously recorded bare-page run. One retry does not establish a statistically reliable speedup.

## Changes tested

The runtime remains one drop-in file: `shopping-agent/shop-agent.js`, version 0.2.0. No platform source edits, backend shopping service, or special agent tool were introduced.

- `products()` now exposes native product images as well as descriptions, attributes and available options.
- `view({ids})` renders up to six products together on the current page, so an ordinary browser screenshot supplies colour evidence without product-page navigation.
- `categories()` exposes native category names and IDs; `search` and `list` accept unique category names.
- PrestaShop exposes its native sale listing via `filters:{onSale:true}` without query/category. This is the same Prices drop listing available in the normal UI.
- `run(async shop => { ... })` executes an ordinary JavaScript callback over the page API. The page help demonstrates batching, local variables and compact result selection. It is not a sandbox or a code-string evaluator. Direct browser JavaScript was already available; this makes the workflow discoverable.
- Up to 500 discovered public references (ID, SKU, URL) survive same-tab navigation. Prices, stock and native payloads are not persisted; detail reads and mutation preflight remain fresh.

Tokens excluding cached input = input − cached input + output. Reasoning output is already included in output. Wall time uses agent task-start and task-complete events and includes final response generation; coordinator setup, tests and verification are excluded. Tool-wait duration is the sum of observed tool-call intervals; the remaining time includes generation, scheduling and overhead, not exclusively reasoning.

One executed Playwright CLI command is one browser interaction; an entire `run-code` script counts as one even when it batches actions. Failed commands count, skipped shell-chain commands do not. Snapshot-file reads and image viewing are excluded. This run executed 11 scripts, 2 screenshots and 2 snapshots.

## Observed remaining overhead

The original category-name error and lost-product-reference error did not recur. There was one new argument error: the agent requested 21 product details against the documented limit of 20, then retried with 14. It had launched six searches in the same `Promise.all`, so those reads were repeated with the corrected details request.

It submitted five search batches totaling 28 queries (including the six launched in the failed combined call). Three category listings exposed filler products, and it tried several drinkware synonyms. The normal sale listing supplied four sale products. The new adapter made these requests accessible but did not choose when the agent should stop searching.

It rendered a six-product comparison, viewed a screenshot, then rendered its final three choices and viewed another screenshot. There was an approximately 45-second interval between the first image-view call and the next browser call; this is an observed gap, not a claim that all of it was visual reasoning.

Browser request observations: 57 fetch requests, 1 XHR, and one document request to `/cart`, excluding initial setup. These are network requests, not agent interactions. Fewer navigations did not mean fewer native read requests.

## Result and verification

The agent selected one each of Canyon V-Neck Tee ($20.80), Trail Pocket Hoodie ($57.60), and Ridge Ribbed Beanie ($17.60). The beanie was its drinkware substitute. It disclosed that fit could not be personalized. Product subtotal was $96; displayed shipping $7; total **$103 USD**. It did not check out.

Independent verification matched native `prestashop.cart` product IDs and quantities to all three visible cart rows. The expected session marker and injected adapter were present. The native cart screenshot was inspected.

Its drinkware searches support “no relevant drinkware found,” rather than an exhaustive proof that the entire catalog contains none. The final recommendation is a flexible substitute, as permitted by the prompt.
